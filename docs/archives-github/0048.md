Closes #13

## Avant
Le score était calculé en SQL, mais aucune partie solo ne pouvait être tirée, jouée puis terminée côté serveur. Les parties anonymes n'avaient ni rétention définie ni budget de création.

## Après
Une partie de dix questions se joue avec ou sans compte via `start_game`, `next_question`, `submit_answer` et `finish_game`. Les tables privées `histoire.games` et `histoire.game_questions` conservent le tirage et les corrections. Les RPC verrouillent la partie, contrôlent son propriétaire et utilisent le score de #12 ; une réponse tardive vaut zéro et deux réponses concurrentes ne peuvent pas écraser le résultat. Une réponse vide est refusée avant la deadline.

Les Server Actions restent minces. Pour les visiteurs, un secret aléatoire de 256 bits est gardé dans un cookie de session httpOnly (Secure en production, SameSite strict) et seule son empreinte est stockée en base. Pour les comptes, l'identité vient de `auth.uid()`. Aucun service_role n'est nécessaire. Avant réponse : titre nettoyé et illustration, sans champ description. Les dates, descriptions privées et alias restent réservés à la correction ; l'ancien correcteur inversé sans partie devient interne pour empêcher le sondage des alias datés.

Les parties anonymes expirent **24 heures après création** : les trois accès sont refusés à expiration, même avec le bon secret et avant suppression physique. Une RPC sans paramètre purge uniquement les anonymes expirées, avec cascade sur leurs questions. Chaque action appelle cette purge dans une transaction distincte ; les créations SQL directes la déclenchent aussi. La purge lors des appels, avec présence possible des lignes expirées sans trafic, a été acceptée par Antonin. Aucun planificateur distant n'est installé.

Un trigger SQL protège les créations anonymes directes et concurrentes avec un budget global initial de **1 000 parties et 10 000 questions stockées**, sous verrou. Renouveler le jeton ne contourne pas ce plafond. Les API ne peuvent modifier ni budget ni expiration. Les parties connectées ne sont ni expirées, ni purgées, ni soumises à ce quota.

## Comment tester
1. Sur un Postgres **vide et local**, lancer `bash scripts/tests-sql.sh` : applique les migrations et le seed, exécute tous les tests SQL et deux transactions concurrentes (réponse et création à la limite du budget).
2. Sur un Supabase local déjà migré, lancer `npm run db:test-solo` et `npm run db:test-solo-retention`.
3. Lancer `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`.
4. Pour brancher la future interface #18 : exports de `src/app/solo/actions.ts` et contrat dans `docs/solo-serveur.md`. Aucune modification graphique.

## Limites et relecture humaine
- Sans trafic, les lignes expirées restent physiquement présentes jusqu'au prochain appel, mais sont inaccessibles ; ce fonctionnement opportuniste est accepté.
- Le quota protège le volume des lignes anonymes, pas le débit de requêtes/CPU/logs. Un attaquant peut saturer le budget et bloquer temporairement les visiteurs. Aucun quota n'est ajouté aux créations connectées, conformément au périmètre demandé. Un contrôle en amont pourra compléter la protection si nécessaire.
- Les plages utilisent leur début ; #14 devra envelopper le correcteur inversé désormais interne dans une RPC autorisée.
- Mise en production de #12/#13 à organiser séparément avec Antonin et Max ; cette PR n'en effectue aucune.
