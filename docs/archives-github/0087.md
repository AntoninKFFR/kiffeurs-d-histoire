## Contexte
Les 24 packs (table `histoire.packs`, événements dans `histoire.pack_events`) viennent tels quels du dataset v18. Maxou et Antonin veulent voir ce que contient chaque pack et retirer les questions qu'ils jugent incohérentes, sans passer par le tableau de bord Supabase ni par un fichier CSV.
Une page réservée aux administrateurs existe déjà : `/admin/indicateurs` (#26), protégée en SQL par `histoire.admins` (voir `docs/indicateurs.md`, `src/lib/indicateurs.ts`). Les dates des réponses ne doivent jamais être lisibles par un joueur : seuls les administrateurs les voient, via des fonctions SQL `security definer`.
Les décomptes affichés dans l'écran de choix viennent de `src/lib/solo/catalogue.json`, généré par `npm run content:catalogue-solo` depuis le dataset.

## Objectif
Sur `/admin/packs`, un administrateur choisit un pack, voit toutes ses questions (titre, date, niveau Débutant/Intermédiaire/Expert, jouable ou non) et peut en retirer une en un clic, avec possibilité d'annuler.

## Tâche pour l'agent
Lis `CLAUDE.md`, `docs/prd.md`, `docs/architecture.md`, `docs/indicateurs.md` et la doc Next.js 16 (`node_modules/next/dist/docs/`).
1. Migration (schéma `histoire` uniquement) :
   - colonne ou table pour marquer un événement **retiré d'un pack** (sans le supprimer : garder qui, quand, pourquoi) ;
   - fonctions `security definer` réservées à `histoire.admins` : lister les packs avec leur nombre de questions jouables, lister les événements d'un pack avec date et niveau, retirer / remettre un événement dans un pack (avec motif facultatif) ;
   - le tirage des parties (`start_game`, mode inversé, tests de chapitre si concernés) ignore les événements retirés.
   - Appliquer la migration sur KFFR avant la fusion (procédure du `README.md`).
2. Page `/admin/packs` dans le style de la charte : liste des packs à gauche, questions du pack à droite, recherche par titre, filtre par niveau, bouton « Retirer » / « Remettre ». Lisible sur PC (pas besoin d'être optimisée mobile).
3. Les décomptes de l'écran de choix (catalogue) ne doivent pas promettre plus de questions qu'il n'en reste : soit les lire depuis la base, soit documenter la commande à relancer après une relecture. Choisir la solution la plus simple et l'expliquer dans `docs/`.
4. Lien vers `/admin/packs` depuis `/admin/indicateurs`.
5. Hors périmètre : créer de nouveaux packs ou éditer le texte des questions (étapes 1.3 à 1.5).
